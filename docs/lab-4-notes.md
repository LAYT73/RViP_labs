# Lab 4 — решения и проверка

Методичка: [task/task.md](../task/task.md), пункт про файловое хранилище. CSV собирает report-service и синхронно отдаёт в file-storage (`HttpService`, это RestTemplate из задания). Файл лежит в S3-совместимом хранилище.

## Что считали неоднозначным

- Куда класть файл: не на диск контейнера и не в Postgres. Отдельный сервис и объектное хранилище. В базе по условию одна таблица, вторая под файлы не заводится.
- Metadata (имя, время) висит на самом объекте. Ключ — `reports/{uuid}.csv`, чтобы имя от пользователя не стало путём.
- Скачивание без консоли S3: `GET /api/files/:id/content` на порту file-storage. Report с хоста по-прежнему закрыт.
- Очередь не входит в эту лабу. Синхронный вызов нужен, потому что так написано в задании. Очередь — lab-5, и там другой ответ API.

Официальный образ MinIO с Docker Hub пропал, поэтому хранилище — `pgsty/silo` с закреплённым тегом, не `latest`.

Пароли в `.env.example` учебные, только для локального compose.

## Что поменяли после внешней проверки

Проверка указала, что любая ошибка S3 выглядела как 404, не было автотестов, образы не были закреплены, а в design было написано «metadata в памяти». Это не совпадало с кодом.

Сейчас нет объекта — 404, хранилище недоступно — 503, report при обрыве POST отвечает 502. Имя файла возвращается в metadata. `pnpm test` гоняет CSV, отказ storage, чтение объекта, пустое и слишком большое тело.

Первый коммит реализации большой: граница сервиса, compose и агентные файлы приехали вместе. Дробить его задним числом не стали. Исправления после проверки — отдельные коммиты.

## Проверка

`pnpm test` — 11 тестов, все зелёные: csv отчёта, POST в storage, 502 если storage не ответил, запись и чтение объекта, 404 против сбоя хранилища, пустой и слишком длинный content.

Ручной путь тот же, что в README: `GET http://localhost:3080/api/reports/by-course/export`, затем `GET http://localhost:3003/api/files/<id>/content`. Если 9000 занят, порты задаются `MINIO_API_HOST_PORT` и `MINIO_CONSOLE_HOST_PORT`.
