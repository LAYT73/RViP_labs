# Lab 5 — решения и проверка

Методичка: [task/task.md](../task/task.md), пункт про очередь. CSV по-прежнему собирает report-service. В file-storage он уходит не POST-ом, а сообщением `report.export.csv`. Клиент сразу получает `{ status: "queued", jobId, rows, filename }`. Файл в S3 появляется, когда consumer его записал.

Хранилище то же, что в lab-4: объект, metadata на объекте, нет ключа — 404, S3 недоступен — 503. Записка по этому слою: [lab-4-notes.md](lab-4-notes.md).

## Что считали неоднозначным

- `jobId` в ответе — это попытка экспорта, не id файла. Id объекта есть только после записи, поэтому в ответ его не кладём.
- Статуса «job готов» нет. Скачивание — `GET /api/files/:id/content` на порту file-storage, когда объект уже лежит.
- JSON `GET /api/reports/by-course` в очередь не ставится. Иначе простой отчёт начал бы зависеть от RabbitMQ.
- Синхронный POST из lab-4 здесь убран специально: иначе лаба не отличается от предыдущей.

## Что поменяли после проверки lab-4

Проверка смотрела синхронный экспорт. На этой ветке те же дыры хранилища закрыты (404 против 503, имя файла, закреплённые образы, методичка в git). Отдельно прогон покрывает то, чего на lab-4 нет: CSV в сообщении, ответ `queued` и имя файла, с которым consumer пишет объект.

Первый коммит очереди большой. Дробить его задним числом не стали.

## Проверка

`pnpm test` — 12 тестов: запись и чтение объекта, 404 против сбоя S3, пустое и слишком длинное тело, заголовок CSV, сообщение с тем же CSV и ответом `queued`, пустое имя файла не становится пустым ключом.

Ручной путь: `GET http://localhost:3080/api/reports/by-course/export` отвечает `queued`. Файл затем забирается с `http://localhost:3003/api/files/<id>/content`, id виден в metadata хранилища. Если 9000 занят: `MINIO_API_HOST_PORT` и `MINIO_CONSOLE_HOST_PORT`.
